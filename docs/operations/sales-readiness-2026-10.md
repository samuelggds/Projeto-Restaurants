# Auditoria para operação comercial em outubro de 2026

Esta revisão corrige falhas de isolamento de sessões, revogação de acesso, concorrência de pagamentos e recuperação operacional. A base inclui a atualização dos planos da PR 292. A liberação depende dos gates do commit final e da implantação das correções; testes locais não comprovam que produção já executa este código.

## Validações reproduzíveis

- `npm --prefix backend test`: descoberta automática dos testes de backend e scripts operacionais.
- `npm --prefix frontend run test:coverage`: 221 arquivos e 1.320 testes passaram na rodada local; statements 64,27%, branches 58,14%, functions 54,79%, lines 66,82%. A correção posterior dos estilos da avaliação passou nos dois testes específicos.
- `npm --prefix print-agent test`: 28 testes passaram, sem hardware.
- `npm run lint`, `npm run typecheck`, `npm run build`, `npm run check:bundle`, `npm run check:architecture`, `npm run check:scripts` e `npm run check:legacy-payments`.
- `npm run test:e2e:critical`: inclui automaticamente as jornadas do navegador. `integrated-stack.spec.ts` tem gate próprio com API e banco reais; `readme-real-ui.spec.ts` produz imagens de documentação e fica separado.
- `node scripts/verifyProductionCompose.mjs`, `node scripts/test-production-release-recovery.mjs` e `bash scripts/test-deploy-production-controller.sh`: configuração e falhas do deploy, incluindo worker indisponível.
- `bash scripts/test-backup-production.sh`: controles com comandos sintéticos; não representa restauração de um backup de produção.
- Auditoria Bulk Advisory dos lockfiles backend, frontend e print-agent sem vulnerabilidades conhecidas retornadas em 07/10/2026. Isso não substitui análise de código, segredos e imagens.

Os resultados autoritativos para mesclagem são os checks do **commit final** no PR: Full Root CI Validation, Security Hardening Validation, Isolated Stack Smoke Validation, Cross-browser Critical Validation e Migration Compatibility Validation. Os novos testes de concorrência e catálogo RLS precisam passar em PostgreSQL real nesse CI. Nenhum gate deve ser ignorado para liberar a versão.

## Limites e implantação

O responsável já informou pagamentos reais funcionando e backup/restauração previamente validados. Esta revisão preserva essas confirmações; não executa novas cobranças reais nem restaura dados de clientes.

A recuperação de resposta perdida segue o contrato oficial de [consulta de Orders do Mercado Pago](https://www.mercadopago.com.br/developers/en/reference/online-payments/checkout-api/search-order/get). Busca vazia, falha ou resultado ambíguo mantém a tentativa pendente e impede nova cobrança. Esse caminho foi testado com respostas simuladas; em operação, casos persistentes exigem conciliação pelo responsável usando evidência do provedor, sem liberar retentativa às cegas.

O inventário cobre as 35 tabelas que já têm RLS. `Order`, `User`, `RestaurantSettings` e `TableSession` continuam protegidos pelo isolamento da aplicação e seus testes; esta mudança não implanta RLS universal. Não há certificação de ausência absoluta de bugs ou vazamentos.

O worker expõe `/ready` somente em `127.0.0.1:3001`, sem porta publicada. Isso valida runtime, banco e transporte de eventos, não o sucesso individual de todos os jobs. Alertas de falhas recorrentes e acompanhamento de reconciliação permanecem necessários. No primeiro rollback para imagem anterior sem esse endpoint, os jobs antigos continuam rodando, mas o healthcheck novo pode marcar o container como `unhealthy`.

O agente de impressão instalado no Windows precisa receber a versão atualizada separadamente do deploy do backend; os testes automatizados não substituem uma impressão física no equipamento do cliente.

Após implantação, conferir o SHA ativo, readiness de API/worker, login/logout de operadores, isolamento entre dois restaurantes de teste e abertura/fechamento de mesa. Preservar os alertas e a rotina de backup já configurados. Os registros locais desta auditoria ficam em `artifacts/production-audit-2026-10-07/`, fora do commit de código.
